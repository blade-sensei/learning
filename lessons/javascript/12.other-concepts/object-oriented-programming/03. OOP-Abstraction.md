
## Introduction

Ce principe est souvent utilisé dans la programmation orienté objet, alors il faut avoir un minimum de compréhension pour nous aider à comprendre des concepts comme l'héritage et la composition ou alors la clean architecture

## Définition

Le but de ce principe est d'abstraire, c'est à dire rendre invisible une partie de notre code, un partie de la compléxité, on veut cacher certains détails.
Autrement dit, on ne s’intéresse qu’à _ce que fait un objet_, pas _comment il le fait_.


Prenons l'example d'une voiture, l'utilisateur de la voiture n'est pas au courant comment fonctionne exactement le moteur, mais il a accès directement à certaines commandes comme les pédales et la voiture vitesse, ce qui lui permet ne pas avoir à toucher à des détails techniques et diminuer le risque de casser quelque chose


Pourquoi cacher certains détails ? 
## Avantages

- **Cacher la complexité interne** et exposer une API simple
- **Favoriser l’extensibilité/modularité** : on peut ajouter de nouvelles implémentations sans toucher aux parties existantes et diminuer le risque de "breaking change" ⭐️
- **Réutilisation** de code: par example avec les classes "abstract" 
- **Rendre le code testable** via des contrats (mocks/fakes) ⭐️
- **Harmonise le code/lecture** en créant des contrats en commun pour des concepts similaires

## 1. Les **Interfaces** — abstraction 100% contractuelle

### 📖 Définition :

Une **interface** est un **contrat** que toute classe peut choisir de respecter.  
Elle **définit la forme** qu’un objet doit avoir, sans aucune implémentation.

### 🧪 Exemple TypeScript :

ts

CopierModifier

```typescript
interface Animal {
  name: string;
  makeSound(): void;
}

class Dog implements Animal {
  name: string;
  constructor(name: string) {
    this.name = name;
  }
  makeSound() {
    console.log("Wouf !");
  }
} 
```

- `Dog` **implémente** l’interface `Animal`, donc il doit avoir une propriété `name` et une méthode `makeSound`.
    

---

### ✅ Avantages/Incovénients :

- Très souple : une classe peut **implémenter plusieurs interfaces**  ⭐️
- Parfait pour les **tests unitaires / mocks** ⭐️
- Permet de faire de la composition, (chose qu'on peut aborder plus tard, mais c'est un technique préféré à l'héritage)
- Ne permet pas de réutiliser du code commun ❌


  

## 📗 2. Les **Classes Abstraites** — abstraction + logique partagée


### 📖 Définition :

Une **classe abstraite** est une classe **incomplète** qui **ne peut pas être instanciée directement**.

  Elle peut :

- contenir des **méthodes abstraites** (sans corps)
- contenir des **méthodes concrètes** (avec du code partagé)

### 🧪 Exemple TypeScript :

```ts
abstract class Animal {
	constructor(public name: string) {}
 
	abstract makeSound(): void;

	move() {
		console.log(`${this.name} se déplace`);
	}
}

class Cat extends Animal {
	makeSound() {
		console.log("Miaou !");
	}	
}
```

---

### ✅ Avantages :

- Permet de **partager du code commun** (par example la méthode "move") 
- Et donc **moins de duplication** que les interfaces ⭐️
- Une seule classe parent possible (`extends`)
- Plus rigide qu’une interface 
- Peut créer un **couplage fort** si mal utilisé  ❌

  

---

## ⚖️ 6. Interface vs Classe Abstraite

  
| Aspect                   | Interface            | Classe Abstraite                |     |
| ------------------------ | -------------------- | ------------------------------- | --- |
| Implémentation           | ❌ Aucune             | ✅ Possible (méthodes concrètes) |     |
| Héritage multiple        | ✅ Oui                | ❌ Non                           |     |
| Contrôle du comportement | ❌ Contrat uniquement | ✅ Contrat + logique partagée    |     |
| Instanciable             | ❌ Non                | ❌ Non                           |     |
| Utilisation idéale       | Contrat léger        | Modèle de base avec logique     |     |

- Les **interfaces** permettent de séparer le "quoi" du "comment"
- Les **classes abstraites** aident à factoriser les comportements communs
---
  
## ✅ Conclusion

- L’abstraction en POO permet de **masquer les détails**, **clarifier les intentions**, et **concevoir des systèmes extensibles**.
- Elle repose principalement sur **les interfaces** (contrats) et **les classes abstraites** (modèles partiels).
- Bien maîtriser abstraction = écrire du code **modulaire, maintenable et testable**.
